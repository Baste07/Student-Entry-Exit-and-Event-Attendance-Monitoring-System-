# Web deployment manifest

This is a **hybrid** installation. `tools/build_web.py` creates the online management package at ignored `dist/web/`. The school workstation continues to run the full `EVENTMONITORING/` tree. Both use the same Supabase project, Auth users, RLS, and AAL2 policy. `DEPLOYMENT_MODE` controls navigation, not authorization. Do not upload the source tree to the web host.

## Build and mount

Set `WEB_SUPABASE_URL` and `WEB_SUPABASE_ANON_KEY` in the build shell, then run `python tools/build_web.py`. The reviewed `tools/web_allowlist.txt` pins every source file; new files are excluded until explicitly added and reviewed. The script writes `dist/web/config/.env.js` with only those **public browser** settings and `DEPLOYMENT_MODE: 'WEB'`; it accepts only a publishable key or an anon-role JWT. `python tools/build_web.py --test-config` creates a deliberately unusable offline test package. Serve the *contents* of `dist/web/` at `/` or `/EVENTMONITORING/` on HTTPS. Do not serve the parent repository or `dist/` itself. Run the package's asset check on every build.

The local workstation's ignored `EVENTMONITORING/config/.env.js` should specify `DEPLOYMENT_MODE: 'LOCAL_GATE'` (the existing config defaults to that). Use the same public Supabase URL and anon key on both installations. The Event, Gate, and Face Registration pages stay on the workstation; local engine PHP/Python stays there. The Local Operations card appears for an AAL2 Admin/Super Admin on the local portal and links the three operation pages through `students/homepage.html`. The web package physically omits those pages, scripts, and PHP routes.

## Deploy (allowlist)

The builder copies `index.html`; `auth/` login, reset, MFA and assets; `portal/`; `admin/` management pages and five public endpoints; `shared/` browser utilities; `config/config.js` and server PHP helper; both modules' management `admin/*.html`, `includes/` header/sidebar, and allowlisted `resc/` CSS, JS, and images. It also includes the shared `Gemma/gemma.css` stylesheet because Super Admin pages import it, **not** the Ollama server or chat UI. The QR sender requires three PHPMailer source files and `students/mail_config.php`, which are copied as server includes and blocked from direct HTTP access. A generated `.htaccess` disables directory listing and direct access to server includes; preserve it on Apache hosting.

Public PHP endpoints (all require a validated Supabase bearer, active Admin/Super Admin, and AAL2 through `admin/admin-mfa-auth.php`): `admin/create-admin.php` (Super Admin), `delete-admin.php` (Super Admin), `admin-mfa-factors.php` (Super Admin), `update-admin-email.php` (Super Admin and explicit server feature switch), `send-student-qr-email.php` (Admin). The latter sends SMTP mail; the others use the server Supabase service-role key. `config/supabase-server.php`, `admin/admin-mfa-auth.php`, and mail/PHPMailer files are **include-only**, not public endpoints. Database grants/RLS and server PHP remain the real authorization boundary.

## Do not deploy

Do not deploy Python, Flask, face capture/recognition, OpenCV/dlib/MediaPipe/MiniFASNet models, `src/`, virtual environments, BAT files, local scanner pages (`students/takeAttendance.html`, `accountRegistration.html`, `manualAttendance.html`, `homepage.html`, `gate/entryExitScanner.html`, `gate/qrAttendance.html`), their JS/CSS, or `admin/engine_log.html`. Also exclude `trigger_attendance.php`, `trigger_registration.php`, `machine_lab_config.php`, `delete_engine_log.php`, `send_event_attendance_email.php`, local XML logs, camera owner, `.npz` caches, runtime machine settings, `Gemma/main.py`, `find_mail_files.php`, `admin/sample.php`, test/debug files, `TEST/`, `.artifacts/`, migrations, build scripts, and repository metadata. Legacy `auth/register.*` is excluded because its professor signup writes the supplied password into a profile row; restore it only after that flow is redesigned and secured. The event attendance email route is local because its callers are the local scanner/manual attendance flow. Face data uploads occur on the local registration service to Supabase Storage, not the PHP host. Management QR mail uses a remote QR rendering API and SMTP; it does not need persistent host upload storage.

## Server-only configuration

Set `SUPABASE_URL` and `SUPABASE_SERVICE_ROLE_KEY` **only** as PHP process environment variables through the host's server configuration. Set `GMAIL_APP_PASSWORD` there for QR mail. `GMAIL_ADDRESS` is a public sender setting in `mail_config.php`. The PHP helpers also support a local ignored `students/.env` fallback, but the web package deliberately excludes it; do not upload that fallback to a public document root. Do not place server secrets in `.env.js`, source control, or a browser response. `admin/update-admin-email.php` additionally requires its documented server-side enable flag and project-ref guard when intentionally used. The local Python service uses its own ignored `.env` and local tokens; those are not web-host settings.

## Auth and URLs

In Supabase Auth URL Configuration, set Site URL to the actual HTTPS web mount and add the exact `https://<host>/<optional-prefix>/auth/reset-password.html` redirect URL. Preserve local development redirect URLs separately. Password reset now derives the path from the current login page, so both `/` and `/EVENTMONITORING/` mounts work. Login/MFA/portal redirects are relative. Review email-confirmation templates and any additional redirect targets before enabling them; the existing admin creation flow confirms email administratively and MFA enrollment stays in the browser session. See [Supabase redirect URL guidance](https://supabase.com/docs/guides/auth/redirect-urls).

## Hosting requirements and controls

Use PHP 8.0+ syntax support; PHP 8.2+ is preferred. Required PHP extensions/functions: cURL, JSON, OpenSSL, and outbound HTTPS to Supabase Auth/Data APIs. PHPMailer requires outbound SMTP to Gmail with STARTTLS on port 587 and a server-provided App Password; `file_get_contents` must be allowed to retrieve the QR image over HTTPS, or the QR sender needs a cURL fallback before production. Apache needs `mod_authz_core`, `.htaccess` override support, and `mod_headers` for the existing no-cache rules. No URL rewriting or local cron is required for the management pages. TLS/HTTPS is required for protected admin sessions. No Python, webcam, ML libraries, or VPS are inherently required for this package: ordinary PHP hosting is enough **if** these extensions, environment configuration, outbound connections, and access controls are available. Supabase handles database and Storage; PHP needs only temporary processing space. Static/CDN fonts, icons, charts, export libraries, and the QR rendering API consume browser/network bandwidth and remain external dependencies.

No endpoint sets permissive `Access-Control-Allow-Origin`; keep browser PHP calls same-origin. Never serve PHP source as text. Keep display_errors off on the host, log server exceptions privately, and use generic client-facing error messages. The package's `.htaccess` rules are for Apache; Nginx or other hosts must implement equivalent deny rules. Verify `/config/supabase-server.php`, `/admin/admin-mfa-auth.php`, `/TimeInAndTimeOutMonitoring/students/mail_config.php`, and directory indexes return 403/404 before deployment.

## Remaining validation before upload

The offline package/route check can confirm local engines are absent and management assets resolve, but a real browser sign-in, MFA, Supabase queries, QR SMTP delivery, email reset, and permission flows require a test host with a valid Supabase project and test accounts. Test those over HTTPS from both root and prefixed mounts. Separately run a live local camera/engine check on the school workstation; static tests cannot prove camera or face-model behavior. This document does not authorize upload, DNS, Supabase changes, or production deployment.
