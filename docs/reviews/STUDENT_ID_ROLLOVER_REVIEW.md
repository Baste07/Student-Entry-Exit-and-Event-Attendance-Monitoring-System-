## Grade model and backfill

- `students.student_id` is the permanent UUID used by guardian, attendance, log, face, and event links.
- `students.stud_id` is a mutable grade-prefixed display ID and the authoritative source of current academic grade.
- Production has no student-level grade field. The proposed migration adds nullable `students.current_grade_level` and validates values from Kinder through Grade 10.
- Every valid `stud_id` prefix is mapped directly to current grade, including inactive rows so reactivation is consistent. `K` maps to `Kinder`; `1` through `10` map to `Grade 1` through `Grade 10`. Production read-only inspection found 40 valid IDs and no malformed IDs. The three dummy IDs `1-0016`, `1-0018`, and `1-0034` will backfill to `Grade 1` despite their differing section grades. No existing UUID, ID, or section is changed by backfill.
- A database check rejects a conflicting or NULL current grade for a valid ID prefix. New student inserts initialize the grade from a valid ID if omitted. Registration/import explicitly supplies it; the edit form can correct a verified grade and display-ID prefix together, keeping the serial and UUID.
- `section_id` remains the persistent group assignment. `sections.grade_level` is section metadata; a different student current grade does not block rollover.

## Rollover

The plan requires a source and following school year, a due date, valid active IDs, agreement between each active student's `stud_id` prefix and `current_grade_level`, and no target-ID collision. It never requires a next-year section. On execution, it atomically advances `stud_id`, `current_grade_level`, and `school_year_id`; it does not update UUID or `section_id`. Grade 10 and inactive students are skipped and reported. Invalid IDs, unverified/conflicting current grades, and collisions keep the year pending for daily retry. History primary key, advisory lock, and transaction provide exactly-once processing. A failed write rolls back all changes.

Default end date is March 25. The daily Cron job runs at 16:05 UTC, which is 00:05 the following day in Manila. The migration has a named-job existence check so a rerun does not add a second job. A new/reissued QR contains `student_uuid:<UUID>`; legacy ID-only QR requires reissue after rollover. Face matching remains UUID-based and its display metadata refreshes outside the per-frame recognition path.

## Application paths

Student current grade now drives Event grade targeting and individual participant filters; Event attendance labels and analytics; Entry/Exit analytics, logs, reports, QR/manual/face labels; both student lists, grade filters, and exports; face registration displays; Event manual attendance email metadata; QR reissue email labels; and student registration/import/edit. Event section targeting still selects section names/IDs independently of grade. Section management, section pickers, and section lists still read `sections.grade_level` as metadata.

The separate `20260927_students_security.sql` migration is prepared and passed development tests, but has not been deployed to production.
